# Scenario 07: Suspicious Login and Possible Account Compromise Investigation

## Overview

This scenario investigates suspicious Microsoft Entra sign-in activity associated
with one pseudonymised user account.

The supplied telemetry records successful access from two materially different
client environments within approximately 107.3 seconds. The investigation examines
the sign-in sequence, authentication steps, MFA results, Conditional Access status,
token-claim reuse, cloud-resource access and available risk indicators.

The analysis distinguishes between:

1. conclusions supported directly by the supplied Microsoft Entra sign-in records;
   and
2. the controlled-lab ground truth published with the Splunk dataset.

## Investigation Objectives

The investigation sought to determine:

1. whether the recorded sign-ins were successful or unsuccessful;
2. which behaviour triggered the suspicious-login investigation;
3. whether the source IP, client, browser, operating system and application context
   differed materially;
4. how the password, MFA, token-claim and sign-in-flow records should be
   interpreted;
5. whether Conditional Access or Microsoft Entra risk detections were applied;
6. whether successful access occurred from more than one client environment;
7. which Microsoft cloud resources were accessed;
8. whether the sign-in telemetry independently proved account compromise or
   browser-session hijacking; and
9. which containment, recovery and detection actions would be appropriate in a
   production environment.

## Data Source and Provenance

The scenario uses a public Splunk Attack Data dataset associated with the
**Azure AD Concurrent Sessions From Different IPs** analytic.

The publisher states that the controlled dataset was generated by using Evilginx2
to obtain an authenticated Azure AD session cookie and importing the stolen cookie
into another browser.

The raw source evidence is stored locally at:

```text
evidence/raw/azuread.log
```

The raw file is excluded from Git. Only the processed, minimised investigation
outputs are intended for publication.

The publisher states that usernames, IP addresses and tenant-specific values were
replaced before publication. Geographic labels in the records are therefore used
only to distinguish the two recorded contexts and are not treated as verified
physical locations.

### Client-environment comparison

| Source IP | ASN | Environment label | Operating system | Browser |
|---|---:|---|---|---|
| `35.1.2.153` | `16509` | Oregon-labelled | Windows 10 | Firefox 108.0 |
| `50.1.2.43` | `12271` | Buffalo-labelled | macOS | Chrome 108.0.0 |

The operating-system, browser, ASN and User-Agent differences establish two
materially different client environments.

They do not independently prove that two physical devices were involved because
the device-identification, management and session-ID fields are unpopulated.

## Key Timeline

1. At `23:13:31`, the Oregon-labelled Windows and Firefox environment supplied the
   correct cloud password and entered an MFA flow.

2. At `23:13:41`, the Oregon-labelled flow recorded completed Mobile app MFA.
   Result code `50140` represented the Keep me signed in interruption rather than
   a rejected password or failed MFA challenge.

3. At `23:13:59`, approximately 18 seconds later, the Buffalo-labelled macOS and
   Chrome environment successfully accessed OfficeHome using first-factor and MFA
   claims already present in the token.

4. At `23:14:02`, the Buffalo-labelled environment successfully accessed Azure
   Portal using existing authentication claims.

5. At `23:14:31`, the Buffalo-labelled environment recorded password and Mobile app
   MFA activity. Two identical raw source records associated with one of these
   authentication events were deduplicated.

6. Between `23:14:36` and `23:14:46`, the Buffalo-labelled environment recorded
   successful identity-layer access associated with Azure Portal, OfficeHome,
   Microsoft Graph, Office365 Shell and Exchange Online.

7. At `23:15:19`, the Oregon-labelled environment recorded a later successful
   Azure Portal access event.

Activity from the two environments was interleaved within the short investigation
window. The available records do not contain session identifiers proving that two
physical devices maintained simultaneous active sessions.

## Authentication Findings

All unique events record `multiFactorAuthentication` as the authentication
requirement.

Where a new challenge was shown, Mobile app notification was the recorded MFA
method. Several successful requests state that the first-factor or MFA requirement
was satisfied by a claim already present in the token.

An existing MFA claim means that Microsoft Entra accepted an earlier
authentication claim for that request. It does not independently prove either MFA
bypass or authorisation by the account owner.

Result code `50140` represents a Keep me signed in interruption. It must not be
counted as a successful sign-in or described as a failed password or rejected MFA
challenge.

## Conditional Access and Risk Findings

Every unique record reports the top-level Conditional Access status as
`notApplied`.

The records contain metadata referring to Per-user MFA, Security Defaults, or both,
but they do not demonstrate that a custom Conditional Access policy was applied.

All unique events contain:

- `riskLevelDuringSignIn: none`;
- `riskLevelAggregated: none`;
- `riskState: none`;
- empty risk-event arrays; and
- `flaggedForReview: false`.

These fields establish that no Microsoft Entra risk detection was recorded in the
supplied events. They do not establish that the activity was benign or authorised.

## Cloud-Resource Access

The events record successful identity-layer access associated with:

- Azure Portal;
- OfficeHome;
- Microsoft Graph;
- Office365 Shell WCSS-Server; and
- Exchange Online.

These records demonstrate successful authentication and authorisation to the named
resources.

They do not prove that any specific email was read, sent, deleted or forwarded;
that files were accessed or downloaded; that directory objects were enumerated; or
that data was exfiltrated.

## Investigation Verdict

### Telemetry-only assessment

The supplied sign-in records establish:

- successful access by the same account from two source IPs;
- materially different client environments;
- successful access from both environments within a short interval;
- use of existing first-factor and MFA claims for several requests;
- access associated with multiple Microsoft cloud resources;
- no applied custom Conditional Access result; and
- no recorded Microsoft Entra risk detection.

The telemetry-only disposition is:

> **True Positive — suspicious concurrent or rapidly alternating access and
> possible account compromise.**

The sign-in records do not independently identify the unauthorised environment or
prove how authenticated session material was obtained.

### Ground-truth-informed assessment

Splunk states that Evilginx2 was used to obtain an authenticated Azure AD session
cookie and that the stolen cookie was imported into another browser.

When this controlled-lab ground truth is included, the disposition is:

> **True Positive — simulated malicious browser-session hijacking involving stolen
> session-cookie reuse.**

The ground truth establishes how the dataset was generated. The cookie theft and
cross-browser import are not directly visible in `azuread.log`.

## Severity and Escalation

The telemetry-only severity is assessed as **medium-high** because successful
access occurred from materially different client environments and involved
multiple cloud resources.

The severity becomes **high** when the controlled-lab ground truth confirms reuse
of stolen authenticated session material.

The event should be escalated for identity-compromise investigation and
containment.

Critical severity is not assigned because the evidence does not demonstrate a
privileged-account compromise, persistence, destructive changes, data
exfiltration, financial loss, service disruption or production business impact.

## MITRE ATT&CK Mapping

| Evidence level | ATT&CK ID | Technique | Tactic | Use in this scenario |
|---|---|---|---|---|
| Publisher analytic mapping | `T1185` | Browser Session Hijacking | Collection | Retained because Splunk maps the concurrent-session analytic and dataset to this technique |
| Controlled-lab ground truth | `T1539` | Steal Web Session Cookie | Credential Access | More directly describes the publisher-stated acquisition and reuse of an authenticated session cookie |

The supplied `azuread.log` does not directly record browser manipulation, cookie
contents, cookie theft, or cookie import. The ATT&CK mappings therefore describe
the publisher's controlled attack context rather than behaviours independently
proven by the sign-in telemetry.

Phishing and Adversary-in-the-Middle are relevant attack-method context because
the publisher states that Evilginx2 was used. The supplied evidence does not
contain the email, URL, proxy, DNS, TLS or network telemetry required to observe
those behaviours directly.

## Evidence Boundaries

The available evidence does not independently establish:

- which environment belonged to the legitimate user;
- which environment belonged to the simulated attacker;
- who approved either Mobile app notification;
- which cookie or token was obtained;
- whether the same browser cookie or refresh token crossed between the two IPs;
- whether the client environments represented separate physical devices;
- how the user reached the phishing infrastructure;
- whether email messages or files were viewed;
- whether mailbox rules, forwarding or permissions were changed;
- whether data was downloaded or exfiltrated; or
- whether production business impact occurred.

No identical correlation ID or unique token identifier appears across both source
IP addresses.

## Response Priorities

In a production environment, the immediate priorities would be to:

1. validate the activity with the user through a trusted channel;
2. revoke active sessions and refresh tokens;
3. reset the password and require secure reauthentication;
4. review registered MFA methods and device registrations;
5. investigate Microsoft Entra audit and Microsoft 365 Unified Audit Log activity;
6. review mailbox, SharePoint, OneDrive and Microsoft Graph operations;
7. examine endpoint, email, proxy and DNS telemetry for the suspected phishing
   path; and
8. preserve evidence and scope other affected accounts or sessions.

See [recommended-actions.md](recommended-actions.md) for the complete containment,
eradication, recovery and hardening plan.

## Detection Opportunities

Recommended detection improvements include:

- correlate successful sign-ins for the same user within a short rolling interval;
- compare ASN, operating system, browser, User-Agent, device identity and
  application context rather than source IP alone;
- count only confirmed successful sign-ins such as `resultCode = 0`;
- do not classify result codes `50074` or `50140` as successful access;
- remove exact duplicate records before aggregation;
- retain detections even when native risk fields are `none`;
- enrich alerts with managed-device and compliant-device status;
- prioritise access to sensitive resources and privileged accounts; and
- correlate suspicious sign-ins with subsequent audit, mailbox, file and
  administrative activity.

See [detection-opportunities.md](detection-opportunities.md) for detailed detection
logic and validation guidance.
