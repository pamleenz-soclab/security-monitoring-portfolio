# Dataset Decision Record

## 1. Investigation Objective

This scenario investigates whether the available identity telemetry represents a
benign anomaly, an unsuccessful attack, suspicious successful sign-in activity,
a successful unauthorised login, or confirmed account compromise.

The analysis separates conclusions supported directly by the sign-in logs from
the controlled-attack ground truth supplied by the dataset publisher.

## 3. Dataset Generation and Ground Truth

According to Splunk, the dataset was generated by using Evilginx2 to phish an
Azure AD user and steal authenticated session cookies. The stolen cookies were
then imported into another browser and used to access Azure AD resources from a
different source IP and location.

This publisher description establishes the controlled-lab ground truth as
browser session hijacking. The sign-in records themselves do not directly
contain the stolen cookie, the phishing interaction, or the Evilginx2 activity.
Those facts must therefore be identified as dataset ground truth rather than
findings independently proven by `azuread.log`.

Splunk also states that tenant-specific values, including tenant identifiers,
usernames and IP addresses, were replaced. Geographic labels and IP ownership
must not be treated as accurate real-world attribution.

## 5. Selection Rationale

The dataset was accepted because it:

- contains Azure AD sign-in telemetry relevant to an enterprise identity
  investigation;
- supports analysis of authentication results and MFA steps;
- provides IP, location, application, browser, operating-system and User-Agent
  context;
- contains correlation and token identifiers that support event grouping;
- allows two concurrent client environments to be compared;
- is static evidence that can be analysed safely offline;
- has a documented simulation method and ground truth;
- has a clearly identified public repository and licence; and
- supports reproducible parsing and timeline reconstruction.

## 6. Available Evidence

The dataset provides evidence for:

- one Azure AD user principal name and user identifier;
- sign-in success, interruption and authentication-step results;
- MFA requirements and authentication methods;
- source IP, ASN and substituted location information;
- applications and resources accessed during the sign-in flows;
- browser, operating system and User-Agent information;
- interactive browser sign-ins;
- sign-in IDs, correlation IDs and unique token identifiers;
- risk-related fields recorded in the sign-in events; and
- the approximately two-minute period represented by the captured events.

These fields are sufficient to establish that two materially different browser
environments successfully accessed the same account during overlapping time
periods.

## 7. Evidence Not Available

The following evidence is not included:

- the phishing message or phishing-site telemetry;
- Evilginx2 logs;
- the stolen session cookie or other session material;
- a reliable pre-incident user, device, network or location baseline;
- device IDs, managed-device status, compliance status or trust type;
- a populated session ID connecting activity across the two source IPs;
- Microsoft Entra directory audit logs;
- Microsoft 365 Unified Audit Log records;
- mailbox access, message-send, deletion, forwarding or Inbox Rule events;
- SharePoint, OneDrive or file-access audit records;
- endpoint, EDR, DNS, proxy or firewall telemetry;
- password-reset, session-revocation or containment records; and
- evidence of data loss, fraud or other business impact.

Consequently, `azuread.log` alone cannot establish who operated each browser,
independently prove how session material was acquired, or confirm post-login
mailbox, file, directory or administrative activity.

## 8. Data-Quality and Interpretation Limitations

### Replaced identifiers

Splunk replaced tenant-specific identifiers, including usernames and IP
addresses. The displayed locations and network ownership are therefore
simulation attributes rather than reliable attribution evidence.

### Inconsistent geolocation

Records labelled as Buffalo contain inconsistent coordinates. The geographic
data may support detection of a location inconsistency, but it cannot confirm
physical travel between the displayed cities.

### Duplicate record

The raw file contains 15 JSON records but only 14 exact unique records.
Investigative counts must distinguish raw-record count from deduplicated-event
count.

### Missing device and session identifiers

Browser and operating-system differences indicate two client environments, but
they do not uniquely identify physical devices. The absence of device and
session identifiers prevents definitive device ownership or cross-IP session
correlation.

### Risk fields

The recorded Entra risk fields contain `none`. This means no risk detection is
recorded in the supplied events; it does not establish that the activity was
authorised or safe.

### Simulated environment

The dataset represents a controlled attack simulation rather than normal
production activity. It is suitable for investigating evidence interpretation
and detection logic, but not for estimating production false-positive rates.

## 9. Safety, Licence and Publication Decision

The selected evidence is a static text log and is analysed offline. No live
phishing infrastructure, session cookie or credential is accessed during the
investigation.

The Splunk Attack Data repository is published under the Apache License 2.0.
The dataset may be referenced with attribution; however, the original
`azuread.log` will remain in `evidence/raw/` and will not be committed to the
public portfolio.

Public GitHub material will contain only:

- the source and licence attribution;
- the evidence hash and metadata;
- sanitised derived timelines and summaries;
- necessary non-secret identifiers; and
- documented analytical conclusions and limitations.

## 10. Dataset Decision

**Decision: Accepted for Scenario 07 with documented limitations.**

The dataset is suitable for investigating concurrent successful sign-ins,
authentication and MFA behaviour, browser-environment differences, geographic
anomalies and possible session hijacking.

Two conclusion layers must remain separate:

1. **Sign-in-log assessment:** suspicious successful sign-in activity and
   possible account compromise. The sign-in telemetry alone cannot independently
   confirm session-cookie theft or identify which environment was unauthorised.
2. **Controlled-lab ground truth:** Splunk confirms that Evilginx2 was used to
   steal authenticated session cookies and that the cookies were imported into
   another browser. In the simulation context, this represents confirmed browser
   session hijacking.

The dataset is not sufficient for Scenario 08 because it contains no Microsoft
365 mailbox audit records. Mailbox compromise, Inbox Rule abuse, email access,
email sending and business impact remain unable to confirm.

The primary MITRE ATT&CK mapping retained for this dataset is **T1185 Browser
Session Hijacking**. Additional techniques will only be added if independently
supported by the available evidence.
